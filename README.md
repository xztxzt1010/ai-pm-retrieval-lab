# AI PM Job Retrieval Lab

> 把分散的 AI 产品经理招聘信息，变成一个**可检索、可追溯、可评测**的岗位知识库。

这是我的 AI 产品经理求职作品之一。项目从一个真实的求职问题出发：面对不同公司、不同方向的岗位描述，如何快速回答“哪些岗位需要 RAG？”“哪些岗位强调 SQL？”“Agent 经验在哪些岗位更重要？”，并且让每个答案都能回到原始来源，而不是停留在主观总结。

我将 11 份 AI 产品经理公开招聘岗位快照整理为结构化语料，完成了 TF-IDF 检索基线、CLI 与网页演示、50 题评测集以及可追溯的能力分析。当前版本刻意不包装成向量 RAG：它首先建立一个简单、透明、可复现的基线，为后续语义检索升级提供可比较的起点。

## 我想解决的不是“做一个搜索框”

求职者阅读岗位描述时，真正需要完成的是三类任务：

1. **快速定位**：从多份 JD 中找到涉及 RAG、Agent、SQL、模型评测等能力的岗位。
2. **横向比较**：识别不同公司和岗位方向对产品能力、技术理解与项目经验的共同要求。
3. **保留证据**：任何结论都能回到岗位文件、原始标题和招聘来源，避免“AI 总结看起来合理但无法核验”。

因此，这个项目的交付闭环不是单一检索功能，而是：

```text
公开岗位信息
    ↓ 整理与统一结构
可追溯岗位语料
    ↓ 切块、分词、建立索引
TF-IDF 检索基线
    ↓ 行为测试 + 50 题评测
可核查质量指标
    ↓ CLI + Showcase
可体验的求职研究工具
```

## 核心结果

当前语料指纹为 `d44eec111a5f7e20`，包含 11 份岗位文件、44 个检索片段。固定评测结果如下：

| 指标 | 结果 | 它回答的问题 |
| --- | ---: | --- |
| Recall@5 | **1.000**（40/40） | 相关岗位能否进入前 5 条结果？ |
| MRR | **0.930** | 正确结果通常排在多靠前？ |
| Precision@1 | **0.875**（35/40） | 第一条结果有多大概率正确？ |
| 引用正确率 | **1.000**（40/40） | 返回的来源与标题能否被原文验证？ |
| 无关拒绝率 | **0.800**（8/10） | 面对语料外问题，系统能否拒绝回答？ |

我保留了两条未正确拒绝的近失配题——“产品经理年薪多少”和“大模型岗位薪资待遇”。它们说明词法匹配会被“产品经理”“大模型岗位”等高相关词触发，也是下一阶段需要用语义判别或更合理拒绝策略解决的问题，而不是应该隐藏的失败样本。

完整评测方法、逐题结果和限制见 [检索评测报告](reports/retrieval-evaluation.md)。

## 从产品问题到工程实现

| 工作环节 | 我的处理方式 | 对应的产品能力 |

| 产品交付 | 同时提供 CLI、网页检索和能力分析报告 | 原型落地、结果表达、使用体验 |
| 风险管理 | 固定语料边界、保存基线快照、记录失败题、声明第三方材料权利边界 | 可信度、合规意识、范围控制 |

## 为什么先做 TF-IDF，而不是直接接入向量库？

这是一次有意的产品与技术取舍：

- **先建立可解释基线**：词项、权重、分数和来源都容易核查。
- **降低复现成本**：不依赖模型 API、密钥、外部向量服务或网络环境。
- **让升级有比较对象**：后续加入 BM25、embedding 或混合检索时，可以继续使用同一评测框架衡量实际增益。
- **主动暴露能力边界**：词法检索擅长明确关键词，不擅长同义改写和深层语义匹配。

这也意味着项目当前是**检索与评测基线**，不是向量 RAG，更没有用生成模型包装检索结果。

## 系统如何工作

```text
kb/jobs/*.md
    │
    ├─ 按二级标题切块
    ├─ jieba 中文分词 + 领域词典
    ├─ TF-IDF 稀疏向量
    └─ 余弦相似度 Top-K
            │
            ├─ CLI：kb/search.mjs
            ├─ API：showcase/server.mjs
            └─ 页面：showcase/showcase.html

同一份语料
    ├─ 15 条行为与边界测试
    ├─ 50 题检索评测
    └─ 岗位能力抽取式统计
```

检索只索引 `kb/jobs/*.md` 中的 11 份岗位文件。README、隐藏文件、依赖目录、评测文件和报告都不会进入语料，并由自动化测试持续约束。

## 如何验证

```bash
# 15 条行为与边界测试
npm test

# 重跑 50 题评测
npm run eval

# 测试 + 评测的一键验证
npm run verify

# 从岗位语料重新生成能力分析
npm run capability
```

评测集包含：

| 类型 | 数量 | 示例目标 |
| --- | ---: | --- |
| exact_match | 15 | 公司、岗位、专有工具等明确锚点 |
| concept | 15 | Agent、RAG、Prompt、数据驱动等能力概念 |
| cross_doc | 10 | 跨岗位比较 SQL、Python、评测等要求 |
| no_answer | 10 | 天气、行情以及与岗位相关但语料无答案的问题 |

基线与最新运行结果分别保存在 `baseline-tfidf.json` 和 `current.json`，便于发现语料或算法变化带来的指标漂移。

## 下一步

下一阶段不会只追求“换一个更先进的模型”，而会继续用指标验证每次升级是否真正改善用户任务：

1. 增加语义改写与近义表达题，扩展当前评测集。
2. 建立 BM25 基线，与现有 TF-IDF 结果对照。
3. 引入本地 embedding，测试语义召回能力。
4. 使用 RRF 组合词法与向量结果，验证混合检索增益。
5. 在检索质量稳定后，再评估是否增加带引用的生成式回答。
